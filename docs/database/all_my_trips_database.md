# All My Trips PostgreSQL 데이터베이스 설계서

## 1. 설계 기준

- 대상 DBMS: PostgreSQL 16 이상, UTF-8
- 데이터베이스명: `all_my_trips`
- 로컬 이미지는 `pgvector/pgvector:pg16`을 사용하고 `citext`, `pgcrypto`, `vector` 확장을 활성화한다.
- 숫자 PK는 `GENERATED BY DEFAULT AS IDENTITY`, 시각은 `TIMESTAMPTZ`, 구조화된 가변 값은 `JSONB`를 사용한다.
- 이메일은 `CITEXT`로 대소문자와 관계없이 유일하며, 대표 이미지·처리 중 신고는 부분 유일 인덱스로 제약한다.
- Redis 대기열·TTL·분산 락은 PostgreSQL에 중복 저장하지 않는다.
- Spring AI PGVectorStore의 `vector_store`는 인프라가 관리하는 임베딩 테이블이며 아래 39개 비즈니스 테이블 수에는 포함하지 않는다.

| 연관관계가 있는 테이블들(도메인) | 설명 |

| `users` → `ai_chat_sessions` → `ai_chat_messages`; `users` → `ai_generation_requests` | AI 일정·최적화·챗봇 사용 이력과 화면 대화 문맥을 관리한다. |

| `users` + `trips` → `travel_records` → 이미지·댓글·좋아요·공유·신고 | 완료 여행 후기와 소셜·관리자 신고 처리를 관리한다. |

| `users` → `reservations` → `reservation_items` → `issued_tickets` → `ticket_validation_logs`; `reservations` → `payments` | 모의 예약·멱등 결제·개별 전자 발권·검표 이력을 관리한다. |

## 5. 핵심 무결성

- 여행 기록은 `COMPLETED` 여행에 여행 소유자가 최대 1건만 작성한다.
- 추천 이벤트는 반드시 실제 `recommendation_results`를 참조하며 이벤트 사용자와 추천 세션 사용자가 같아야 한다.
- AI 메시지와 연결된 AI 요청은 같은 `ai_chat_session_id`에 속해야 한다.
- 공유 토큰 원문, 전자 티켓 검증 토큰 원문, 결제 인증정보는 저장하지 않는다.
- 티켓 재고는 옵션별 사용 날짜·시간대 단위로 관리하고 `reserved_quantity <= total_quantity`를 보장한다.
- 결제는 `idempotency_key`를 유일하게 유지해 중복 승인을 차단한다.
- 항공·숙소 외부 링크, 날씨 API 캐시, Redis 대기열은 비즈니스 테이블 범위 밖이다.

## 7. PostgreSQL·RAG 운영 원칙

- `JSONB`는 AI 원본 입출력, RAG 근거 부가정보, 관리자 변경 전후 스냅샷처럼 속성이 가변적인 감사·문맥 데이터에만 사용한다.
- 추천 결과의 장소·순위·점수·이유는 `recommendation_results`로 정규화했으므로 기능 확장 시 JSON 내부 검색에 의존하지 않는다.
- 임베딩 차원은 사용하는 모델에 따라 달라질 수 있으므로 Flyway가 고정 `vector(n)` 비즈니스 테이블을 만들지 않고 Spring AI PGVectorStore 설정이 `vector_store`를 관리한다.
- 위치 반경 검색이 주요 기능으로 확정되면 PostGIS 도입과 `geography(Point,4326)` 전환을 별도 마이그레이션으로 검토한다. 현재는 지도 표시용 위도·경도를 `NUMERIC`으로 유지한다.
- `updated_at`은 공통 `set_updated_at()` trigger로 갱신하며 애플리케이션 enum과 CHECK 허용값을 함께 변경한다.

## 8. 실행 SQL 구조

```text
database/
├── init/create_database.sql       # 관리자용 DB 생성
├── init/create_extensions.sql     # 관리자용 citext·pgcrypto·vector 확장
├── migration/V1~V7               # PostgreSQL Flyway DDL
├── schema/all_my_trips_schema.sql # V1~V7 통합 실행 DDL
├── seed/local_seed_*.sql          # PostgreSQL 합성 데이터
├── validation/validate_seed_data.sql
└── README.md
```

실행 순서는 `init → V1~V7 → users → places → trips → ai → records → tickets → validation`이다. 전체 통합 DDL은 `database/schema/all_my_trips_schema.sql`에서 확인한다.

## 9. 알려진 제한사항

- 업무지시서의 `COMPLETED` 여행이 4건이므로 여행당 기록 1건 무결성을 우선해 여행 기록 seed도 4건만 생성한다.
- 여행 소유자 일치, 완료 여행만 기록 가능, 댓글과 답글의 동일 기록 소속 같은 행 간 규칙은 Service와 validation SQL에서 추가 검증한다.
- 테마·추천·AI 화면 요구는 이번 스키마에 반영했지만, 실제 API 계약이 바뀌면 DDL·이 문서를 같은 변경에서 갱신한다.
