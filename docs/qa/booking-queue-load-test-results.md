## 4. 읽는 법

### capacity를 올리면 대기 시간은 반비례로 줄어듭니다

`capacity`를 2 → 20으로 열 배 올리자 p95가 40.8초 → 3.0초로 줄었습니다. 성공·소진 건수는 어느 회차에서나 동일했습니다. **대기열은 누가 먼저 들어가느냐만 조절하며 몇 명이 살 수 있는지는 재고가 정합니다.**

### 이 수치는 서버 지연이 아니라 사용자 체감입니다

스크립트는 화면과 같은 **3초 주기로 순번을 확인**합니다. 그래서 측정값은 "서버가 입장시킨 시각"이 아니라 "사용자가 자기 차례를 알게 된 시각"입니다. 폴링 주기만큼 올림이 되며, capacity 20 회차의 중앙값 0초와 최대 3초가 그 경계입니다.

값을 고를 때는 이쪽이 맞는 기준입니다. 사용자는 서버 내부 시각이 아니라 화면이 바뀌는 순간을 기다립니다. 다만 **폴링 주기를 줄이면 같은 capacity에서도 체감이 줄어듭니다.** capacity와 폴링 주기는 함께 봐야 합니다.

## 5. 권장 값

**기본값 5를 유지합니다.**

- p95 15초는 대기 화면을 보여주는 목적에 맞습니다. 대기열이 실제로 동작하는 것이 보이면서 이탈할 만큼 길지 않습니다
- 10 이상으로 올리면 p95가 6초 아래로 내려가 30명 규모에서는 대기열이 거의 드러나지 않습니다. 기능을 시연하기 어렵습니다
- 2는 실습 규모에서 지나칩니다. p95 40초는 사용자가 새로고침하거나 창을 닫습니다

**다만 이 값은 30 VU · 재고 10 기준입니다.** 실사용 동시 접속이 이보다 크게 늘면 다시 재야 합니다. 지금 근거는 "이 규모에서 대기 화면이 자연스럽게 보이는 선"이지 처리 한계가 아닙니다.

## 6. 측정 도구에서 고친 것

준비물은 이번이 첫 실행이었고, 그대로는 측정이 불가능했습니다. 발견 순서대로 적습니다.

| # | 문제 | 영향 |
| --- | --- | --- |
| 1 | `RedisBookingQueueStore`·`BookingQueueService`가 Jackson 2 `ObjectMapper`를 빈으로 주입받음 | **`local`·운영에서 앱이 아예 기동되지 않음.** `@Profile("!ui")` 때문에 `ui`에서만 감춰져 있었음 |
| 2 | k6가 CSRF 토큰 없이 로그인 시도 | 모든 VU가 로그인에서 403으로 중단 |
| 3 | 모든 VU가 같은 `TRIP_ID` 사용 | 예약은 여행 소유자만 가능해 29명이 거부됨. 측정값이 무의미 |
| 4 | `http_req_failed` 임계값이 재고 소진 409를 실패로 집계 | 정상 동작인데 매 회차가 threshold 위반으로 끝남 |

1번은 대기열 기능 자체의 결함이므로 부하 테스트와 무관하게 고쳐야 합니다.

3번을 고칠 때 `TRIP_ID`를 지우지 않고 남겨 두었습니다. VU 하나로 디버깅할 때는 특정 여행을 고정하는 편이 낫기 때문이며, 지정하지 않으면 각 VU가 `GET /api/v1/trips`로 자기 여행을 찾습니다.

### 로컬 환경에서 걸린 것

`uuid-ossp`와 `hstore` 확장이 없어 Flyway `V10__vector_store.sql`이 실패했습니다. `docker-entrypoint-initdb.d`는 **데이터 디렉터리가 비어 있을 때만** 실행되므로, 볼륨을 만든 뒤에 추가된 확장은 반영되지 않습니다. 오래된 볼륨을 쓰는 사람은 같은 곳에서 막힙니다.

```bash
docker compose exec -T postgres psql -U allmytrips -d all_my_trips \
  -c 'CREATE EXTENSION IF NOT EXISTS hstore;' \
  -c 'CREATE EXTENSION IF NOT EXISTS "uuid-ossp";'
```

## 8. 만료 경로 — 버그가 있었습니다

1차 7절의 마지막 항목입니다. 확인해보니 **실제로 동작하지 않는 경로가 있었습니다.**

대기표가 입장(READY)이 되는 길이 두 개인데, 한쪽만 만료 시간이 제대로 걸려 있었습니다.

| 경로 | 적용된 시간 | |
| --- | --- | --- |
| 줄 서고 → 차례가 옴 (`STATUS_SCRIPT`) | `admission-ttl` (2분) | 정상 |
| 줄 없이 → 바로 입장 (`ENQUEUE_SCRIPT`) | `entry-ttl` (10분) | **잘못됨** |

`ENQUEUE_SCRIPT`가 WAITING이든 READY든 가리지 않고 `entry-ttl`로 만료를 걸고 있었습니다. **2분이면 놓아야 할 자리를 10분간 붙잡고 있었던 셈입니다.**

한산할 때는 대부분 바로 입장하는데 그때는 아무도 안 기다리니 티가 안 납니다. **몰릴 때만 손해가 나는** 종류라 그동안 안 보였습니다.

### 확인 방법

`admission-ttl=8s`로 짧게 주고 Redis 키 수명을 직접 봤습니다.

```bash
docker compose exec redis redis-cli TTL "all-my-trips:booking-queue:entry:<토큰>"
```

| | 입장 직후 대기표 수명 | 9초 뒤 |
| --- | --- | --- |
| 수정 전 | **179초** (= `entry-ttl` 3분) | 14초 뒤에도 예약 성공 |
| 수정 후 | **7초** (= `admission-ttl`) | 조회·예약 모두 410 만료 |

승급 경로도 함께 봤고 원래대로 잘 됩니다(TTL 8초 → 만료). 두 경로가 이제 같아졌습니다.

## 9. 회차별 결과

| 회차 | capacity | 입장 | 성공 | 소진 | 만료 | 평균 | p95 | **응답 p95** | 실패율 | 체크 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| A | **5** (기본) | 30 | 10 | 20 | 0 | 7.55s | 15.06s | **255ms** | 0.0% | 100% |
| B | 10 | 30 | 10 | 20 | 0 | 3.01s | 6.02s | **895ms** | 0.0% | 100% |

**대기 시간은 1차와 같습니다.** 1차 2·3회차(p95 15.0초 / 6.0초)가 그대로 재현됐습니다. 고친 코드에서도 대기열 동작은 변하지 않았다는 뜻입니다.

DB도 매 회차 확인했습니다. `reserved 10 = total 10`, 예약 10건, 서로 다른 사용자 10명. 서버 ERROR 로그 0건.

### 새로 본 것 — capacity를 올리면 서버가 느려집니다

1차에서 안 잰 축입니다. capacity를 5 → 10으로 올리자

- 기다리는 시간 p95: 15.06초 → 6.02초 (**60% 감소**)
- 개별 응답 시간 p95: 255ms → 895ms (**3.5배 증가**)

한 번에 들여보내는 사람이 많아지면 같은 재고를 두고 DB에서 동시에 다투기 때문입니다. **줄이 짧아진 대신 창구가 느려집니다.**

1차 4절의 "capacity를 올리면 대기 시간은 반비례로 줄어듭니다"에 **공짜는 아니라는 단서**가 붙습니다.

### 권장 값 — 기본값 5 유지 (1차와 같음)

결론은 1차와 같고 근거가 하나 늘었습니다. 5에서 응답 255ms는 안정적이고, 10으로 올리면 대기 화면이 거의 안 보이는 데다 응답까지 느려집니다.
